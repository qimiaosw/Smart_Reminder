## 一、项目整体定位

### 一句话说清项目

> 「一个基于用户分层的智能推送系统，通过个性化和频次控制提升学生端任务完成率。」

### 面试官第一反应会问

> 「为什么要做这个？解决了什么实际痛点？」

**你的回答结构（30 秒版）：**

```
现状问题：
  DAU 50 万，但 40% 的学生每天来了就走，任务没完成。
  当前的唯一推送是每天 18:00 一条固定文案「你还有任务未完成」，
  打开率只有 8%。

目标：
  把打开率从 8% 提升到 15%，完成率从 60% 提升到 75%。

方案：
  用用户分层 + 智能引擎做个性化推送，
  让「对的人在对的时间收到对的内容」。
```

## 二、架构总览与分层逻辑

### 2.1 整体架构分层

```
┌─────────────┐
│   React 前端  │  → 任务中心 / 提醒面板 / 设置页 / A/B 管理后台
├─────────────┤
│  Spring Boot  │  → 用户服务 / 任务服务 / 通知服务 / 智能引擎
├─────────────┤
│   RabbitMQ   │  → push.request / push.callback / user.behavior.event
├─────────────┤
│ MySQL+Redis  │  → 持久化 + 缓存 / 频控 / 在线状态
└─────────────┘
```

### 2.2 为什么这么分层

| 层 | 为什么存在 | 如果不分层会怎样 |
|------|-----------|---------------|
| **前端 React** | 任务展示、推送设置、A/B 实验管理 | 纯后端项目没法演示效果 |
| **Spring Boot** | 业务逻辑集中，团队熟悉 | — |
| **RabbitMQ** | 解耦推送请求和推送发送，削峰填谷 | 推送高峰期阻塞，用户等待 |
| **Redis** | 频控计数需要毫秒级读写，MySQL 扛不住 | 频控查表变慢，推送延迟 |
| **MySQL** | 用户、任务、日志需要持久化和复杂查询 | 数据不可靠，无法分析效果 |

### 2.3 面试时这样说

> 「架构设计上我主要考虑三个点：**解耦**（Kafka 把推送请求和发送分开）、**性能**（Redis 做频控计数而不是查 MySQL）、**可扩展**（每个模块职责单一，新增策略不改旧代码）。」

## 三、各模块设计意图解读

### 3.1 用户分层模块

**设这么细的原因：**

> 推送系统的核心不是「怎么发」，而是 **「发给谁」**。如果所有用户收到一样的东西，那跟现在 8% 打开率没区别。

**面试官可能问：**

| 问题 | 你的回答 |
|------|---------|
| 分层依据为什么选 7 天？ | 「7 天覆盖一个完整的学习周期（周一到周日），太短（3 天）噪音大，太长（30 天）反应太慢。」 |
| 规则阈值 80%/40% 怎么定的？ | 「基于当前 DAU 数据和完成率分布做了粗略切分。真正上线后可以通过 A/B 测试调优——切分点本身也可以作为实验变量。」 |
| COLD_START 为什么默认需提醒型？ | 「宁可多发几条，也比新用户来了没任何提醒直接流失好。7 天后再纠正。」 |

### 3.2 频次控制模块

**面试官最想看到的地方——这是最容易出 bug 的模块。**

你有单元测试覆盖：

```java
@Test
void shouldNotSend_whenInQuietHours() { ... }

@Test
void shouldNotSend_whenExceedsDailyLimit() { ... }

@Test
void shouldNotSend_whenIntervalTooShort() { ... }

@Test
void shouldSend_whenAllChecksPass() { ... }
```

**面试时主动提：**

> 「频控是整个系统里业务规则最密集的地方，我专门写了单元测试覆盖所有边界情况——免打扰时段、每日上限、最小间隔。上线后这类逻辑最容易出 bug，测试一定要到位。」

### 3.3 智能提醒引擎

这是项目的 **「灵魂」**，面试官会重点看。

**拆成三个子模块的原因：**

| 子模块 | 职责 | 如果合并 |
|--------|------|---------|
| 时机决策 | 什么时候发 | 耦合在一起，改一个地方影响另外两个 |
| 内容生成 | 发什么 | 后面想接 LLM 得大改 |
| 频次控制 | 能不能发 | 无法独立测试 |

**面试时主动说：**

> 「我把引擎拆成三个独立模块，每个只做一件事。这样以后想换内容生成策略（比如从模板换成 AI）只要改 `PushContentGenerator` 一个接口的实现，时机和频控完全不受影响。」

## 四、七个「留空档」详解——面试怎么接

以下是架构文档第 10 章提到的 7 个扩展点。**每一个都是刻意留的，面试官问到时你有准备。**

---

### 空档 ①：LLM 推送文案

**架构中状态：** `PushContentGenerator` 接口已定义，当前用模板变量实现。

**面试官问：「为什么文案不用 AI 生成？」**

> 「我考虑了。当前先用模板变量，原因是：
> 1. **可控性**——模板文案可以保证不出错，AI 生成可能跑偏
> 2. **成本**——DAU 50 万，每人每天推 1–2 条，全量调 LLM API 成本不低
> 3. **可对比**——模板是基线，后面可以用 A/B 测试对比 AI 文案 vs 模板文案的效果差异
>
> 架构上我已经预留了 `PushContentGenerator` 接口，后续加一个 `AiContentGenerator` 实现类就行。而且可以先小流量测试——让 10% 的用户走 AI 文案，对比打开率差异。」

---

### 空档 ②：流失预测模型

**架构中状态：** 目前用规则判断（连续 3 天未完成 → 流失倾向型）。

**面试官问：「规则判断够用吗？」**

> 「当前 DAU 50 万的量级，规则判断足够了。但如果数据量再大，或者想提前预测流失（在用户还没完全流失之前就干预），规则就不够灵活了。
>
> 架构上我已经在 `user_behavior_events` 表里全量采集行为事件。后续可以做特征工程（近 7 天登录频次、完成率变化趋势、平均在线时长等），用简单逻辑回归或决策树做流失概率预测。特征和训练数据都是现成的，模型上线后也可以用 A/B 测试对比规则引擎和模型的效果。」

---

### 空档 ③：社交提醒

**架构中状态：** 未实现，但推送模板层面预留了扩展。

**面试官问：「你有没有考虑过社交机制？」**

> 「考虑过，但第一期先聚焦推送本身。社交提醒（学习小队、排行榜、同桌互催）是第二期方向。
>
> 为什么第一期不做：社交功能涉及好友关系链、组队逻辑、隐私控制，复杂度比推送大得多。如果一开始就做，项目周期会拉长，核心的智能推送引擎反而没时间打磨。
>
> 但如果要做，现有架构可以直接复用——用户分层模块可以加一个 `group_id` 字段，推送模板可以引用队友进度变量。技术上没有障碍。」

---

### 空档 ④：多通道降级

**架构中状态：** `notification_logs.channel` 字段已设计，支持 `push` / `sms` / `in-app`。

**面试官问：「如果用户关了通知权限怎么办？」**

> 「我考虑了这个问题。`notification_logs` 表已经预留了 `channel` 字段。
>
> 对于流失倾向型用户，如果推送连续 N 次未送达，可以降级到短信或微信模板消息。虽然成本高一些，但针对的是即将流失的用户，ROI 是正的。
>
> 技术上，通知服务可以再加一个 `ChannelRouter`——先调厂商推送，推送失败 → 降级到短信。这个路由逻辑对上游完全透明。」

---

### 空档 ⑤：离线补推

**架构中状态：** 未实现。

**面试官问：「用户离线期间产生的推送怎么办？」**

> 「目前 RabbitMQ 的消息暂存，用户上线后可以扫描 `notification_logs` 中 status = 'pending' 的记录补推。
>
> 但这里有个权衡：补推太多会让用户反感。我的设计是只补推最近一条，而且打上一个「离线补推」的标签，用于后续分析这种方式的打开率。如果效果不好，可以关掉。」

---

### 空档 ⑥：家长端联动

**架构中状态：** 未实现，`users` 表可扩展。

**面试官问：「有没有想过让家长参与？」**

> 「想过但第一期不做。学生产品的家长联动很敏感——处理不好学生会觉得被监视，反而流失更快。
>
> 如果要加，我的设计是：家长只能看到『学习时长』和『完成率』这类统计信息，不能看到具体题目或成绩。推送文案也应该是关心导向（『XX 最近学习有些松懈，可以关心一下哦』）而不是告状导向。」

---

### 空档 ⑦：Widget 桌面组件

**架构中状态：** 未实现。

**面试官问：「除了推送还有什么方式触达用户？」**

> 「桌面 Widget 是一个低成本高回报的方案。学生日均只打开 App 25 分钟，但看手机的次数远超 25 分钟。桌面小组件显示今日任务进度，用户解锁手机就能看到，不需要打开 App，也不依赖推送权限。
>
> 技术上，前端 React 侧可以抽一个独立的 Widget 数据接口，不需要改后端逻辑。」

## 五、技术选型对比——面试官必问

### 5.1 为什么用 RabbitMQ 而不是 Kafka？

```
推送量级：50 万 DAU × 1-3 条/天 ≈ 50-150 万条/天
每秒钟 ≈ 17 条，峰值 ≈ 50 条

这个量级 RabbitMQ 绰绰有余，为什么没有选 Kafka？

-> 三个原因：
  1. 量级匹配 —— RabbitMQ 的设计定位就是几千到几万条/秒的低延迟消息路由，
     当前 50 万 DAU 完全在它的舒适区
  2. 运维成本低 —— RabbitMQ 比 Kafka 轻量得多，单机部署即可，
     不需要 Zookeeper，资源占用也更少
  3. 延迟更低 —— RabbitMQ 的 AMQP 协议是 push 模型，
     消息到达消费者端的延迟通常在毫秒级，比 Kafka 的 poll 模型更适合同步推送场景

如果后续 DAU 增长到千万级别、需要消息回溯或流式处理，
可以通过 MessageQueue 接口抽象，把实现从 RabbitMQ 切换到 Kafka，
对业务代码完全透明。
```

### 5.2 为什么自建 A/B 测试而不是用第三方？

| 维度 | 自建 | 第三方（GrowingIO / Firebase） |
|------|------|-------------------------------|
| 数据隐私 | 用户数据不出自己的服务器 | 数据要传到第三方 |
| 灵活性 | 分组逻辑与用户分层深度耦合 | 只能做简单的流量切分 |
| 成本 | 开发成本一次性 | 持续付费 |
| 实时性 | 实时 | 有延迟（通常 T+1） |

### 5.3 为什么 MySQL 而不是 PostgreSQL？

```
真实原因：团队熟悉 MySQL。
面试话术：
  「当前数据模型是结构化关系型，MySQL 完全够用。
  notification_logs 表后续量大了需要按月分表，
  但 MySQL 的分表方案已经很成熟。
  如果后续需要复杂的 JSON 查询或者全文检索，
  再考虑迁移到 PostgreSQL。」
```

### 5.4 为什么频控用 Redis 而不是 MySQL？

```
原因：频控是每次推送前都要检查，请求量 = 推送量 × 频控检查次数。
如果用 MySQL，每次检查要查表、写表，压力大且延迟高。
Redis 是内存操作，毫秒级响应，天然的 TTL 机制
（每日计数 TTL = 当天结束自动过期）非常适合频控场景。
```

## 六、面试引导话术：怎么把话题引到你的优势区

### 开场自我介绍（1 分钟版）

> 「我做了一个智能提醒系统，核心是**通过用户分层提升推送效果**。
>
> 技术上用了 Spring Boot + React + RabbitMQ + Redis + MySQL。
> 架构上拆了四个微服务，核心是智能提醒引擎，拆成时机决策、内容生成、频次控制三个模块。
>
> 最有成就感的是**A/B 测试框架是自己搭的**，没有用第三方。
> 另外频控模块的**单元测试覆盖了所有边界情况**。」

**引导点：**
- 提到 A/B 测试 → 引导面试官问「为什么自建」
- 提到单元测试 → 引导面试官问「测了什么」

### 项目难点讲述（1 分钟版）

> 「最大的难点是**频次控制**。刚开始想简单点——每天最多 N 条就行了。
> 但实际上要考虑免打扰时段、最小间隔、用户是否在线、不同类型用户限额不同……
> 这些规则叠在一起，很容易漏掉边界情况。
>
> **我的做法是：** 先把规则拆成独立的检查方法，每个方法只做一件事，
> 然后给每个方法写单元测试。最后组合起来再写集成测试。
>
> 这样改一个规则不会影响其他规则，而且测试失败了能立刻知道是哪个检查出的问题。」

**引导点：**
- 提到「拆成独立检查方法」→ 展示模块化设计思维
- 提到「单元测试覆盖边界」→ 展示工程素养

## 七、可能被追问的高频问题

### Q1：「你的分层规则阈值 80%/40% 是怎么来的？」

```
不是拍脑袋。是分析了当前 DAU 的完成率分布后做的粗略切分。
更精确的方式是：取历史数据，画出完成率分布曲线，
在自然的拐点处切分。上线后还可以把切分点本身做成 A/B 实验变量。
```

### Q2：「50 万 DAU 单机部署够吗？」

```
推送场景：
  - 推送计算是定时任务（每 5 分钟扫描一次），不是实时计算
  - 每次扫描量 = 待提醒用户数 ÷ 5 分钟，压力很小
  - 真正的瓶颈在厂商推送通道，不在我们的服务器

所以单机部署完全够。如果后续 DAU 增长到 500 万以上，
可以把用户分片，多个实例各自处理不同分片。
```

### Q3：「短信降级的话成本怎么控制？」

```
短信只对流失倾向型用户使用，这类用户只占 20%。
按 DAU 50 万算，也就是 10 万人，每人每天最多 1 条短信。
短信成本约 0.03–0.05 元/条，每天最多 5000 元的成本。
和挽回一个流失用户的价值相比，这个 ROI 是可以接受的。
```

### Q4：「为什么 notification_logs 不分表？」

```
50 万 DAU × 每人每天 1–2 条推送 = 每天 50–100 万条日志。
一年约 3.6 亿条。单表确实扛不住。
我在架构里写了要按月分表或按用户 ID 哈希分表，
文档里有说明。也可以直接用 TiDB 这种分布式数据库替代 MySQL。
```

### Q5：「你这个项目最大的设计缺陷是什么？」

```
（这是一个陷阱题——面试官想看你能不能自我批判）

「我觉得有两个可以改进的地方：
1. 智能引擎的时机决策目前是轮询扫描（每 5 分钟），
   不是事件驱动。如果要做到真正的『实时』，
   应该改成用户行为事件触发生成推送，而不是定时扫描。
2. A/B 测试的分流算法我用的是 user_id hash mod 100，
   这种方式的问题是如果用户量少，分组会不均匀。
   可以用更稳定的 Consistent Hash 或分层抽样。」
```

## 八、项目演示 Checklist

### 演示前确认

- [ ] Docker 中 MySQL、Redis、RabbitMQ 容器正常运行
- [ ] Spring Boot 项目能正常启动（`mvn spring-boot:run`）
- [ ] React 前端能正常启动（`npm run dev`）
- [ ] 数据库中有测试用户数据（至少覆盖三种用户类型）
- [ ] 推送定时任务触发间隔调整为 1 分钟（方便演示）
- [ ] A/B 测试管理后台有至少一个实验在运行

### 演示流程建议

```
1. 打开前端 → 展示任务中心（30 秒）
   → 「这是学生看到的界面」

2. 展示用户分层（30 秒）
   → 「不同类型的用户收到的推送不一样」

3. 打开 A/B 测试后台（30 秒）
   → 「我正在跑的一个实验：对比 18:00 固定推送 vs 智能时段推送」

4. 展示单元测试（30 秒）
   → 「这是频控模块的测试覆盖」

5. 总结（30 秒）
   → 「总耗时 2.5 分钟」

6. 留时间给面试官提问
```

```
│   │   ├── services/          # API 调用
│   │   └── abtest/            # A/B 实验管理后台
│   └── package.json
├── docker-compose.yml         # MySQL + Redis + RabbitMQ
├── docs/
│   └── 架构设计文档.md
└── README.md
```

> **说明**：包按业务模块划分（user / task / notification / engine / abtest / event）而不是按技术层划分（controller / service / repository）。这样做的好处是：新增一个功能只需要在一个包内加文件，不需要跨多个包跳转。面试官看到这种结构，会觉得你有**DDD（领域驱动设计）**的基本意识。
