## 一、业务背景与现状分析

### 1.1 当前数据

| 指标 | 数值 |
|------|------|
| DAU | 50 万（学生约 30 万） |
| 当日任务完成率 | 60% |
| 未完成任务即离开 | 40%（约 12 万） |
| 现有推送到达率 | ~60%（部分关通知权限） |
| 推送打开率 | **8%** |
| 打开后完成率 | 45% |

### 1.2 当前推送的问题

- **时间固定**：每天 18:00 一条，无视用户个人空闲时段
- **内容固定**：所有用户收到相同文案「你还有学习任务未完成」
- **频次单一**：每天仅 1 次，错过无后续
- **无个性化**：不分用户类型，不分行为习惯

### 1.3 学生行为画像

| 维度 | 数据 |
|------|------|
| 日均在线时长 | 约 25 分钟 |
| 在线高峰 ① | 16:00–18:00（放学后），占 35% |
| 在线高峰 ② | 19:00–21:00（晚饭后），占 45% |
| 连续 3 天以上未打开 | 约 30% 学生 |

## 二、用户分层模型

### 2.1 三层分类

| 类型 | 占比 | 特征 | 策略 |
|------|------|------|------|
| **自律型** | 40% | 每天自主完成任务 | 轻提醒，不骚扰，以鼓励和进度反馈为主 |
| **需提醒型** | 30% | 需要推送才能完成 | 智能定时推送 + 个性化文案 |
| **流失倾向型** | 20% | 提醒也不一定来 | 多渠道触达 + 激励措施 + 提前干预 |
| *(另 10% 为数据稀疏 / 新用户 / 异常)* | | | 冷启动默认策略 |

### 2.2 分层依据（规则引擎）

```java
用户分层规则：
  1. 近 7 天完成率 ≥ 80%                      → 自律型
  2. 近 7 天完成率 40%–80%                     → 需提醒型
  3. 近 7 天完成率 < 40% 或 连续 3 天未完成    → 流失倾向型
  4. 注册 < 7 天 或 数据不足                    → 冷启动（默认需提醒型）
```

> **扩展点预留**：当前为规则判断。后续可接入简单逻辑回归或决策树模型进行流失预测，在用户真正变成「流失型」之前提前干预。

## 三、业务目标与核心指标

### 3.1 核心指标

| 指标 | 当前 | 目标 | 衡量方式 |
|------|------|------|---------|
| 每日任务完成率 | 60% | **75%** | 完成任务数 / 当日应完成数 |
| 推送打开率 | 8% | **15%** | 推送打开数 / 推送送达数 |
| 流失率（7 日未打开） | ~30% | **< 20%** | 7 天内未打开 App 的用户占比 |
| 推送到达率 | ~60% | **> 80%** | 推送送达数 / 推送发送数 |

### 3.2 北极星指标

**「每日任务完成率」**— 它直接关联用户学习效果，是所有优化的最终指向。

**关键接口：**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/v1/users/{id}/profile` | GET | 获取用户画像（分层类型、活跃时段、连续未完成天数） |
| `/api/v1/users/{id}/settings` | PUT | 更新通知偏好（推送开关、免打扰时段） |
| `/api/v1/users/segment/batch` | POST | 批量更新用户分层标签（定时任务触发） |
| `/api/v1/users/{id}/behavior` | POST | 上报用户行为事件（在线/完成任务/离开等） |

**定时任务：**


**微任务设计：**

```java
// 一个大任务拆分为 3–5 个微任务，每个 3–5 分钟完成

```

### 5.4 智能提醒引擎 (Smart Reminder Engine) ⭐ 核心

#### 5.4.1 时机决策模块

```
输入：user_id, user_type, active_time_slot, last_open_time；
输出：最佳推送时间戳

算法：
  1. 有历史打开记录 → 取该用户历史打开时间的 P50（中位数）
  2. 无历史记录但有 active_time_slot → 取时段中点前 30 分钟
  3. 冷启动 → 按分层默认：
     自律型   → 不主动推送，仅在任务发布时发进度摘要
     需提醒型 → 18:00（放学高峰前）
     流失型   → 18:00 + 20:00 双次
  4. 若用户当前在线 → 跳过推送（避免骚扰，下次调度再判断）
```

> **扩展点预留**：当前为规则引擎。后续可引入「任务紧急度权重」——截止时间越近，推送优先级越高。可在 `reminder_rule` 表中加字段扩展，不需改代码。

#### 5.4.2 内容生成模块

**模板变量系统：**

```
自律型   → 「🏆 今日完成率 {rate}%，已超过班上 {percentile}% 的同学」
需提醒型 → 「📚 你还有 {count} 项任务未完成，现在开始只需 {minutes} 分钟」
流失型   → 「🎁 连续学习 3 天可获 {reward}，今天要开始吗？」
连续未完成 → 「学习不用着急，从一个小任务开始吧 👣」
```

> **扩展点预留**：当前为模板变量填充。后续可接入 LLM（如 GPT / 文心），在模板基础上做文案润色或个性化改写。预留了 `PushContentGenerator` 接口，模板生成和 AI 生成可互相切换。

#### 5.4.3 频次控制模块

| 策略 | 自律型 | 需提醒型 | 流失型 |
|------|--------|---------|--------|
| 每日最多推送数 | 0–1 条 | 1–2 条 | 2–3 条 |
| 推送最小间隔 | — | ≥ 2 小时 | ≥ 2 小时 |
| 免打扰时段 | 21:30–07:00 | 21:30–07:00 | 21:30–07:00 |
| 用户在线时 | 不推送 | 不推送 | 不推送 |
| 二次推送 | 无 | 1h 未完成补一次 | 次日 10:00 加一次 |

### 5.5 A/B 测试框架

**为什么自建而不是用第三方 SDK：** 推送策略 A/B 测试需要与用户分层、行为数据深度耦合，自建更灵活且不依赖外部服务。

**数据模型：**

```sql
CREATE TABLE ab_test_experiments (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100),           -- 如「推送时机优化 V1」
    status VARCHAR(20),          -- DRAFT / RUNNING / ANALYZING / COMPLETED
    target_user_type VARCHAR(20), -- 测试目标用户分层
    start_at DATETIME,
    end_at DATETIME,
    created_at DATETIME
);

CREATE TABLE ab_test_groups (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    experiment_id BIGINT,
    group_name VARCHAR(50),      -- control / variant_a / variant_b
    config_json JSON,            -- 推送时机/内容/频次的具体配置
    user_count INT DEFAULT 0,
    traffic_percent INT          -- 流量占比，如 50 / 25 / 25
);

CREATE TABLE ab_test_assignments (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(32),
    experiment_id BIGINT,
    group_name VARCHAR(50),
    assigned_at DATETIME
);
```

**前端展示：** React 管理后台展示实验列表、实时指标对比（打开率/完成率/置信区间）。

## 六、数据库设计

### 6.1 MySQL 核心表

#### users 表

```sql
CREATE TABLE users (
    id VARCHAR(32) PRIMARY KEY,
    username VARCHAR(100) NOT NULL,
    real_name VARCHAR(100),
    user_type VARCHAR(20) NOT NULL DEFAULT 'COLD_START',
    -- 可选值: SELF_DRIVEN / NEED_REMINDER / DROPOUT / COLD_START
    push_enabled BOOLEAN DEFAULT TRUE,
    active_time_slot VARCHAR(20),        -- 如 "19:00-21:00"
    consecutive_miss_days INT DEFAULT 0,
    last_active_at DATETIME,
    push_token VARCHAR(255),             -- 厂商推送 Token
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at DATETIME DEFAULT NULL,    -- 软删
    version INT DEFAULT 0,               -- 乐观锁
    INDEX idx_user_type (user_type),
    INDEX idx_deleted_at (deleted_at)
);
```

### 6.2 Redis 缓存设计

| Key | 类型 | Value 说明 | TTL | 用途 |
|-----|------|-----------|-----|------|
| `push:daily:{userId}` | String | 当日已推送次数 | 当天 23:59:59 过期 | 每日频控上限 |

## 七、核心数据流

### 7.1 推送发送主流程

```
定时任务 (Cron: 每 5 分钟扫描)
    │
    ▼
智能提醒引擎查询「待提醒用户列表」
    │
    ├── 时机决策模块 → 判断是否到推送时间
    ├── 内容生成模块 → 选择模板 + 填充变量
    ├── 频次控制模块 → 检查限额/间隔/免打扰
    └── A/B 测试路由 → 按实验分组选择策略
    │
    全部通过
    │
    ▼
发送到 RabbitMQ exchange: push.request
    │
    ▼
通知服务 Worker 消费 RabbitMQ
    │
    ├── 组装推送消息
    ├── 调用厂商推送通道（FCM / 华为 / 小米）
    ├── 写入 notification_logs（MySQL）
    └── 更新 Redis 频控计数
    │
    ▼
用户点击推送
    │
    ▼
前端回调 → 发送到 RabbitMQ exchange: push.callback
    │
    ▼
通知服务更新 notification_logs.opened_at
    │
    ▼
用户完成任务
    │
    ▼
任务服务 → 更新 daily_tasks 状态
           → 写入 user-behavior-events
           → 触发下一轮提醒策略调整
```

### 7.2 画像更新流程

```
用户行为事件
  (打开App / 完成任务 / 关通知 / 离开)
    │
    ▼
前端 / 服务端 → 发送到 RabbitMQ exchange: user.behavior.event
    │
    ▼
用户服务定时消费 (每 5 分钟)
    │
    ├── 更新 user_profile 统计字段
    ├── 计算连续未完成天数
    └── 检测是否需要变更分层标签
    │
    分层变更 ?
    │
    ├── 是 → 更新 users.user_type
    │       → 发送到 RabbitMQ（通知提醒引擎调整策略）
    └── 否 → 继续累积数据
```

### 7.3 冷启动流程

```
新用户注册
    │
    ▼
用户服务 → user_type = COLD_START
    │
    ▼
前 7 天：
  ├── 推送策略 = 需提醒型默认策略
  ├── 活跃时段 = 统计活跃时间分布
  └── 7 天后 → 按规则重新分层
```

> **面试留空**：冷启动目前用 7 天默认策略。可优化方向：注册时可做简单问卷（「你通常几点有空学习？」），或参考同学校/同年级用户的分布做协同过滤初始赋值。

## 十一、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 推送频率过高导致用户关通知 | 推送渠道失效，后续所有优化白费 | 严格频控（硬限制 + 可配置）、免打扰时段、用户可自定义设置 |
| 智能时段判断不准确（冷启动） | 效果不及预期 | 冷启动默认策略 + 7 天行为积累后重新分层 + A/B 验证 |
| RabbitMQ 消息积压导致推送延迟 | 推送错过最佳时机 | 监控队列长度 + 设置告警 + 高峰期前预消费 |
| MySQL 表数据量增长（notification_logs） | 查询变慢 | 按月分表 + 保留 90 天历史自动归档 |
| 厂商推送通道不稳定 | 推送到达率下降 | 多厂商通道冗余 + 失败重试 + 降级到站内信 |
